# Merge vs Rebase

Два способа интегрировать изменения из одной ветки в другую. Оба валидны, выбор зависит от ситуации.

## Merge

```bash
git switch main
git merge feat/install-guide
```

- Создаёт **merge commit** с двумя родителями.
- История ветвистая, но честная: видно, что было параллельной разработкой.
- Не переписывает уже опубликованные коммиты — безопасно для общих веток.

## Rebase

```bash
git switch feat/install-guide
git rebase main
```

- Переписывает коммиты ветки так, как будто они сделаны поверх свежего `main`.
- История линейная, чистая.
- **Меняет SHA коммитов** → опасно, если ветка уже у кого-то ещё.

## Когда что использовать

| Сценарий                                              | Что делать                  |
|-------------------------------------------------------|-----------------------------|
| Локальная feature-ветка, ещё не запушена              | rebase — чистит историю     |
| Long-lived ветка с PR, открытым ревью                 | merge — не ломает SHA       |
| Подтянуть свежий main в свою ветку перед PR           | rebase, если только сам(а) пушил |
| Подтянуть свежий main в общую ветку                   | merge                       |
| Закрыть PR в default                                  | merge или rebase-and-merge  |

## Pull rebase vs pull merge

```bash
git config --global pull.rebase true   # git pull = git fetch + git rebase
git config --global pull.rebase false  # git pull = git fetch + git merge
```

Для journey-репо (где работает один человек) — `pull.rebase=true` даёт линейную чистую историю.

## Чего не делать

- `git rebase` опубликованной ветки, на которой работают другие — порвёшь им жизнь.
- `git merge` в feature-ветку из main с целью «обновиться» — лучше `rebase`, иначе у тебя в ветке появятся merge-коммиты, которые потом будут мешать.
